# 防折叠混淆算法深度指南

## 问题背景

### 为什么需要防折叠？

微信朋友圈自 2017 年起对营销内容、重复转发进行自动折叠，目的是改善用户体验。但对于内容创作者（特别是多人团队），这造成了问题：

- 同一条文案，多个成员转发 → 被识别为重复 → 折叠显示
- 同一账号短时间发多条 → 自动折叠成一行
- 特定词汇 → 营销账号识别 → 触发审核

### 旧算法的致命缺陷

之前的 v1.0 实现使用**均匀间隔的零宽字符插入**：

```javascript
// 旧代码（有问题）
const step = Math.floor(result.length / totalInserts);  // 确定性间隔
for (let i = 0; i < totalInserts; i++) {
    const insertPos = (i + 1) * step;  // 每次计算都一样
    result = result.slice(0, insertPos) + char + result.slice(insertPos);
}
```

**问题**：
- 用户 A 复制文案 → 位置 [10, 20, 30...] 插入零宽字符
- 用户 B 复制同一条 → 位置 [10, 20, 30...] 插入零宽字符
- 微信看到完全相同的混淆结果 → 仍然识别为重复 ❌

## 新算法：RLO/PDF + 完全随机

### Unicode 排版方向控制字符

#### RLO（Right-to-Left Override, U+202E）
- **作用**：强制让后续文本从右到左显示（阿拉伯文、希伯来文的标准）
- **在中文中的效果**：字符顺序反向

#### PDF（Pop Directional Formatting, U+202C）
- **作用**：结束 RLO 的效果，恢复正常方向

#### 实际例子

```
原文本：
  我见过很多企业家

使用 RLO/PDF 混淆后的字符顺序：
  我 + RLO + 过 + 见 + PDF + 很多企业家

显示效果（用户看到的）：
  我见过很多企业家  ← 完全正确！

微信的文本分析看到的：
  我‮过见‬很多企业家  ← 字符序列被打乱

哈希值对比：
  原文哈希：   abc123...
  混淆哈希：   xyz789...  ← 完全不同！
```

### 关键优化：完全随机化

新算法在三个维度实现随机：

#### 1. 随机选择混淆位置
```javascript
// 不再固定间隔，而是：
const maxStart = sentence.length - subLen;
const startPos = Math.floor(Math.random() * (maxStart + 1));  // 随机选择
```

#### 2. 随机选择混淆范围
```javascript
const subLen = Math.floor(Math.random() * (maxSubLen - minSubLen + 1)) + minSubLen;
// 2-4 字的短语随机选择
```

#### 3. 随机选择混淆顺序
```javascript
if (Math.random() < 0.6) {
    result = antiFoldWithRLORandomly(result, cfg.rlo);      // 60% 先用 RLO
    result = antiFoldWithZeroWidthRandomly(result, cfg.zw);
} else {
    result = antiFoldWithZeroWidthRandomly(result, cfg.zw);  // 40% 先用零宽
    result = antiFoldWithRLORandomly(result, cfg.rlo);
}
```

### 效果对比

同一条文案，三个人各复制一次：

```
原文：
我见过很多企业家。外人看他们：有钱，有团队，有地位。

用户 A 复制：
我‮过见‬很多企业家。外人‮看‬他们：有钱，‍有团队，有地位。

用户 B 复制：
我见‌过很‮多企‬业家。外‮看人‬他们：有钱，有‌团队‍，有地位。

用户 C 复制：
我见过‌很‬多‮企业‍家‬。外人看‮他‬们：‍有‮钱‬，有团队，有‌地位。
```

**结果**：
- 三个文案的哈希值完全不同
- 微信看不出它们是重复的
- 各自独立发布 ✅

## 微信的反制措施

微信的防作弊团队可能会采取的措施：

### 已知对我们有效的
- ✅ RLO/PDF 字符（目前被识别为正常排版控制字符）
- ✅ 零宽字符（被许多应用用于其他目的）
- ✅ 低密度混淆（不影响阅读体验）

### 微信可能会做的
- ⚠️ 在文本分析时忽略 RLO/PDF（可能）
- ⚠️ 建立"防折叠文案"的特征库（已有迹象）
- ⚠️ 提升账号级别的识别（不只看单条文案）

### 应对策略
1. **保持低调** - 不要大量使用，不要在同一账号短时间内多次发
2. **分散发布** - 多个账号、多个时段
3. **内容多样化** - 不要每次都用相同的表述
4. **配合其他方法** - 部分重点内容放在图片上

## 扩展思路

### 如果 RLO/PDF 被识别怎么办？

备选方案（按推荐度排序）：

1. **变体字符**
   - 简体繁体混淆：「我」vs「我」（肉眼难分）
   - 同形异码字符：「А」(西里尔) vs「A」(拉丁)

2. **特殊空格**
   - 普通空格、不换行空格、半角空格混用
   - 微信可能没有完全规范处理

3. **标点符号变化**
   - 「。」vs「．」vs「。」
   - 改变表达逻辑但意思不变

4. **分词重组**
   - 原：「限时特惠」→ 改为：「限│时│特│惠」
   - 插入微妙分隔后，分词算法可能失效

### 测试方法

1. **本地对比**
   ```bash
   # 复制两次同一条文案
   copy1=$(node -e "console.log(antiFoldProcess('测试文案'))")
   copy2=$(node -e "console.log(antiFoldProcess('测试文案'))")
   
   # 检查是否不同
   [ "$copy1" != "$copy2" ] && echo "✓ 混淆成功" || echo "✗ 混淆失败"
   ```

2. **微信实际测试**
   - 多个账号各发一次
   - 观察 72 小时内是否被折叠
   - 记录数据，用于优化

3. **字节分析**
   - 用 HexDump 对比两次生成的结果
   - 确认 RLO/PDF 位置确实是随机的
